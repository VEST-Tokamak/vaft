Design principles and methodological foundations

Design principles and methodological foundations

At a glance

Architecture position
Research and methodological foundations of VAFT, their distinct relationships, and evidence-backed mappings to current code and documentation.
Prerequisites / inputs
Scientific architecture; no running database or solver required.
Expected result
Understand which ideas inform VAFT, which mechanisms exist, and which standards or research-publication capabilities are not claimed.
Status
Maintained against the pinned develop baseline.

VAFT integrates experimental records, physical models, computation and research practice. Its design is informed by several complementary traditions, not derived from a single FAIR standard. This page explains those traditions and maps them to scientific architecture, computational layers, scientific credibility and inspectable implementations. It is an explanatory guide, not a certificate of compliance, an evidence of universal portability, or a claim of scientific correctness.

The original scientific infrastructure principles diagram deliberately provides a compact two-sided overview: cross-disciplinary FAIR / PROV / TRUST principles and fusion-community methodological requirements. The first diagram below is its expanded documentary interpretation, not a silent replacement for the versioned vaft.diagram.scientific_infrastructure_principles() asset.

Reading the relationships

Four relationships must not be conflated:

Relation Meaning Appropriate example
Extends / adapts One published framework explicitly develops another FAIR4RS adapts FAIR for research software; workflow FAIR guidance adapts FAIR to executable workflows
Complements Independent frameworks address different scientific concerns FAIR access does not establish numerical validity; V&V addresses different questions
Informs An intellectual or methodological precedent motivates a VAFT choice OMFIT’s integration practice informs composition of codes and data, without implying common software architecture
Implemented through A specific VAFT component realizes a design mechanism Registry-defined relations are rendered by the scientific ontology explorer

A conceptual similarity is not evidence of historical derivation or implementation of a formal standard. In particular, recording provenance is not the same as serializing W3C PROV, and making a result machine-readable does not prove its physical validity.

Principle-to-implementation evidence map

Statuses refer to named mechanisms, never to overall FAIR / PROV / TRUST certification. Implemented means the linked source or guide explicitly documents a concrete mechanism; it does not mean it has been independently evaluated for scientific effectiveness. Partial denotes a narrower realization than the referenced methodological programme. Context denotes influence rather than a software feature.

Lineage or concern Design requirement Implementation evidence Assessment
FAIR (Wilkinson et al., 2016) Discoverable, accessible, interoperable and reusable research data Data access and IMAS; database sources Implemented mechanisms; no complete FAIR audit claimed
FAIR4RS (Barker et al., 2022) Reusable, versioned and documented research software Generated API catalog; documentation build; release process Implemented documentation and release mechanisms; no principle-by-principle certification
FAIR computational workflows (Goble et al., 2020; Wilkinson et al., 2025) Inspectable executable composition and workflow provenance Automated pipelines; pipeline lineage Implemented workflows; FAIR publishing/discovery not fully assessed
Provenance (W3C PROV, 2013) Distinguish inputs, activities, agents, versions and derived products Pipeline lineage; machine mapping provenance Implemented native records for pipeline stages and VEST shot-processing revisions; not enforced uniformly for every code; PROV exchange conformance unverified
TRUST (Lin et al., 2020) Explain access, repository governance and long-term responsibility Database and data sources; contacts Partial; trustworthy-repository certification not claimed
Semantic interoperability (Vogt et al., 2025) Explicit concept identity, mapping, relations and unresolved ambiguity Ontology explorer; typed relation generator Implemented typed semantics; no universal semantic equivalence
Born-readable scientific findings (Stocker et al., 2025) Produce structured scientific resources during research, including context and evidence Ontology; validation evidence; immutable study/run records Partial: production-time structured registries and validation artifacts, and immutable study records for the ML workflow; publication-linked findings and external knowledge-graph aggregation unverified
Integrated modelling (Meneghini and Lao, 2013; IMAS) Compose heterogeneous scientific codes and data without conflating methods Scientific architecture; computational layers Implemented design and code interfaces; portability depends on device mapping
Scientific credibility / V&V Separate source evidence, transformation, inference, applicability, numerical checks and independent validation Credibility and applicability; validation taxonomy Implemented taxonomy and selected assessments; not a universal physical guarantee
Reproducible documentation (Ram, 2013) Link generated descriptions to source revisions, catch broken relationships Documentation build; diagram guide Implemented for registered catalogs and assets
Longitudinal scientific knowledge recovery Preserve period-dependent machine conventions and explain uncertainty rather than silently rewriting history Diagnostics registry; machine mapping Implemented selected VEST mappings; archive completeness is a separate measurement
Human-readable and machine-accessible interfaces Expose the same scientific descriptions to people and software agents Documentation; read-only MCP adapter Implemented access mechanism; agent reasoning gains not evaluated

What “born-readable” does and does not mean here

Stocker et al.’s reborn research programme distinguishes (1) producing machine-readable expressions of findings while analysis is performed, (2) depositing the structured findings and connecting them to publications, and (3) collecting them in knowledge-graph aggregation systems.

VAFT already supports a substantial part of stage 1: scientific quantities and relationships are described in source-controlled registries; analysis produces IMAS/OMAS data and machine-readable validation artifacts; individual study workflows can emit structured, content-addressed records. The ontology encodes relations such as measures, represented_by, consumes, produces, assumes and assessed_by. The experiment store records linked study, run, evaluation, decision and manifest objects for the ML research workflow; that specific implementation should not be generalized to every VAFT workflow.

VAFT does not thereby demonstrate a single canonical repository-wide research-claim object that binds every numerical conclusion to its primary evidence, nor publication DOI linkage, deposited claims, or ORKG ingestion. These narrower gaps concern interoperability with the full reborn publication lifecycle, not absence of production-time machine-readable scientific work.

Why human interpretation still matters

Data-path compatibility, semantic identity, and physical interchangeability are distinct. A field in the IMAS equilibrium IDS can be numerically loadable without containing sufficient profile information for downstream MHD stability analysis. An inferred quantity is not a direct measurement; a converged calculation can violate its physical model’s validity conditions. Consequently:

  • Data / numerical interoperability makes representations exchangeable.
  • Semantic interoperability makes concept identities and relations explicit.
  • Scientific qualification evaluates evidence, assumptions, scope and physical applicability for a particular use.
  • Human and AI interpretability depends on exposing all three through documentation, diagrams, plots, notebooks and bounded agent interfaces.

These are complementary design goals; no one entails the others. The ontology explorer, credibility taxonomy and MCP interface expose different facets of that relationship. Expert review remains necessary when recovering historical calibration rules or resolving ambiguous scientific conventions.

Scope and maintenance

This page describes the code and documented behaviour on the branch used to build it. For a release or manuscript citation, use a fixed commit or release, not a mutable documentation URL alone. Prefer generated source links and registries over copying implementation details into narrative text. When a mechanism changes, update its evidence link and assessment here.

The following are not established by this page: formal FAIR or TRUST certification; W3C PROV interchange compatibility; complete historical coverage; uniform enforcement of provenance for all codes; machine-to-machine portability without qualified mapping; or demonstrated improvement of agent accuracy or research productivity.
